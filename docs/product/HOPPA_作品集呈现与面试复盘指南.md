# HOPPA 求职作品集呈现与面试复盘指南

> 原则：如实区分原始方案、后续产品重构、AI 辅助开发和真实用户验证。

## 1. 作品集应该讲什么

不要把叙事重点放在“我用 AI 写出了很多页面”。建议围绕完整产品决策链：

**发现问题 → 明确用户与场景 → 提出产品假设 → 做 MVP 取舍 → 设计核心流程 → AI 辅助实现 → 测试与迭代 → 复盘下一步。**

推荐标题：**HOPPA｜从“搭子文化”到活动闭环的同城轻社交产品重构**

一句话介绍：HOPPA 面向希望通过具体活动拓展同城体验的年轻人，围绕活动发现、偏好匹配、组队管理和活动后分享，降低从线上认识到线下参与的组织成本。

## 2. 项目展示结构（建议 8–10 页）

1.  **项目封面**：产品名、口号、项目角色、时间、演示链接 / QR。
2.  **问题与场景**：用户在什么时刻需要找搭子；为什么现有方式不够顺畅。除非有访谈证据，否则将结论标为假设。
3.  **目标用户与 JTBD**：参与者、活动发起者、城市探索者。
4.  **产品定位与方案**：为什么以活动为关系起点；产品如何完成线上到线下闭环。
5.  **MVP 取舍**：P0 做闭环，P1 做体验增强，P2 暂缓高成本和高风险能力；解释为什么暂缓 3D 元宇宙、真实定位、真实报警和复杂 AI。
6.  **核心流程与关键页面**：活动发现、详情、申请、活动管理、群聊、签到、评价 / 旅行名片。
7.  **Vibe Coding 过程**：如何把 PRD 拆成阶段任务，要求 Agent 检查仓库、实现、测试和修复。
8.  **验证方案 / 结果**：若已做测试，展示真实任务完成率、问题和改版；若尚未测试，展示计划与待验证假设，不伪造结果。
9.  **指标体系**：北极星指标、漏斗指标、安全护栏及口径。
10. **复盘与路线图**：做得好的决策、不确定部分、下一阶段如何验证。

请根据实际情况替换方括号内容，不要把计划写成已完成成果。

**HOPPA｜同城轻社交与活动组队产品（个人产品重构 / AI 辅助开发）** - 基于本科阶段的搭子文化产品方案与移动端原型素材，重构产品定位与 MVP 范围，将原有多模块概念收敛为“发现—申请—组织—参与—评价”的核心闭环。 - 输出 PRD、页面交互规格、数据模型、验收清单与事件埋点口径，明确 P0/P1/P2 优先级及真实定位、紧急求助、身份核验等高风险功能的演示边界。 - 使用 \[实际使用的工具 / 技术栈\] 进行 Vibe Coding，实现 \[实际完成的页面与流程\]；通过 \[真实执行的测试方法\] 验证 \[实际观察到的结果\]。 - 根据 \[访谈 / 可用性测试 / 自测\] 发现 \[真实问题\]，完成 \[真实迭代\]，并规划以活动详情点击率、申请转化率和活动完成率验证核心假设。

## 4. 面试时最值得讲的产品决策

### 为什么不先做 3D 元宇宙？

3D 城市展示成本高，且不是验证“用户能否找到合适活动并完成线下参与”的必要条件。先用活动卡片、路线节点和轻量城市内容验证核心价值；若用户确实需要空间探索，再考虑三维体验。

### 为什么不用 MBTI 直接决定匹配？

MBTI 可以是可选的自我表达标签，但不能代表真实行为偏好或安全性。首版优先使用活动类型、时间、预算、出行方式和明确兴趣进行透明匹配，并解释推荐原因。

### 如何解决冷启动？

从一个城市、少量活动类型和明确时间段开始。用精选路线与示范活动提供初始供给，优先验证活动是否能被看见、申请和完成；再根据供需情况扩展品类与城市。这是待验证的策略建议。

### 怎么定义产品成功？

试点阶段可将“每周完成的有效活动数”作为北极星指标，并用详情点击率、申请转化率、活动完成率和评价完成率诊断漏斗。安全指标必须作为护栏，不能只追求转化。

### 你如何使用 AI，而不是依赖 AI？

把 AI 当作执行伙伴：先定义需求、状态机、数据结构和验收标准；再分阶段生成代码；每阶段运行构建、检查交互和边界；对安全、数据、体验和最终结论负责。重点展示你做了哪些决策、发现了什么问题以及如何验收，而不是只展示生成速度。

## 5. 最低限度的用户验证计划

邀请 3–5 位目标用户做任务测试： - 找到一个预算不超过 100 元的周末活动并申请。 - 创建一个 City Walk 活动并设置人数与费用规则。 - 从“我的活动”进入进行中活动并完成模拟签到。 - 对已结束活动评价并查看旅行名片。

记录任务完成与否、完成时长、错误 / 回退次数；用户是否能准确复述时间、集合地点、预算和费用方式；用户在哪一步犹豫或担心安全；用户认为最有价值的功能和可删除的功能。

3–5 人的探索性测试不能描述为统计显著的结论。展示发现的问题、迭代前后截图和决策理由，比空泛的“用户满意度很高”更有说服力。

## 6. 作品集中的诚信边界

- 旧文档里的市场统计属于历史材料；对外引用前应重新核验来源和时间。
- Mock 数据不是运营数据。
- 原型里的“紧急求助”不是实际报警能力。
- 静态路线不是实时导航。
- AI 生成代码不等于已经完成代码审查；应说明实际测试范围。
- 没做过的用户访谈、实验、上线和商业合作，不得写成已完成。
