# HOPPA Vibe Coding 开发任务书

> 目标：把已有 HOPPA 产品方案与 UI 参考开发为可运行、可交互、可重复演示的求职作品集 MVP。 适用：Codex、Cursor、Claude Code、Lovable 或其他代码 Agent。请根据实际工具能力执行，不要声称未执行的测试已经通过。

## 1. 角色与成功标准

你同时承担资深前端工程师、产品实现负责人和 QA 的职责。不要只生成静态页面，必须实现关键交互、状态流转、本地数据持久化、错误处理和运行说明。

成功标准： 1. 能在本地启动并运行。 2. UI 保留 HOPPA 粉紫、暖白、浅桃色和圆角卡片风格。 3. 能演示“发现活动 → 查看详情 → 申请加入 → 组织者审核 → 群聊 → 模拟签到 → 活动结束 → 评价 / 旅行名片”。 4. 能演示“创建活动 → 发布 → 管理申请 → 推进活动状态”。 5. 刷新后，用户创建的活动、申请、消息、个人资料和评价仍然存在。 6. 不调用真实 GPS、电话、公安接口、支付、短信或未配置的外部 API。 7. README 写清启动命令、演示身份切换、主要流程、测试结果和已知限制。

## 2. 开始前必须做的事

- 检查当前仓库目录、现有代码、package.json、README、环境变量和已有组件。
- 如果仓库已有应用，先理解结构并沿用现有技术栈；不要重写无关功能。
- 如果目录为空，默认 React + TypeScript + Vite；样式可用 Tailwind CSS；路由可用 React Router；图标用 Lucide。
- 先输出简短实施计划和文件结构，再开始编码。
- 不索取或硬编码 API Key；本 MVP 不依赖外部 API。
- 不把用户提供的截图直接当作整页背景。参考品牌和信息结构，重新构建可响应组件。

## 3. 产品基线

产品：HOPPA，同城轻社交与活动组队。口号：线上相遇，线下来聚。首发城市：武汉。核心用户：18 岁及以上、希望通过具体活动认识同好或探索城市的年轻人。核心价值：活动信息透明、偏好筛选、低压力组队、从线上匹配走到线下参与。

开发范围以 `HOPPA_PRD_v1.0.md` 和 `HOPPA_交互与页面规格_v1.0.md` 为准。如文件名不同，先读取仓库内文档并遵循 P0 范围。遇到冲突时，保留已有实现，列出冲突并询问；不要擅自扩展范围。

## 4. 页面与导航

必须有以下可用页面：首页 / 发现、同城、找搭子、活动详情、创建活动、我的活动、活动管理、消息 / 活动群聊、路线规划、个人中心、安全中心、评价 / 旅行名片。

桌面端使用完整可浏览布局；移动端使用底部主导航。页面在 375px 宽度下应可操作，在 1280px 桌面宽度下应保持良好层级。

## 5. 核心数据与状态

至少实现：User、Activity、Application、ActivityMember、Conversation / Message、Review、Post（可简化）、Report、SafetyCheckin（仅模拟）。ID 稳定唯一；状态枚举集中定义；避免在多个组件散落硬编码状态文本。

活动状态： - preparing（准备中） - ongoing（进行中） - awaiting_review（待评价） - completed（已结束） - cancelled（已取消）

申请状态： - pending（待审核） - approved（已通过） - rejected（已拒绝） - withdrawn（已撤回） - left（已退出）

必须保证： - 发起者自动成为组织者 / 成员，不用申请自己的活动。 - 已通过人数不得超过 maxParticipants。 - 满员、已取消、已结束活动不能再申请。 - 同一用户不能重复提交同一活动的有效申请。 - 活动时间必须在未来；关键字段缺失时不能发布。 - 只有活动结束后才允许评价；同一用户对同一活动只能评价一次。 - 状态流转按 PRD 约束，不允许任意跳转。

## 6. 数据持久化与演示模式

- 使用 mock seed data 初始化 10–15 条武汉活动，覆盖 City Walk、美食、展览、桌游、运动、演出。
- 首版使用 localStorage 持久化，不需要真实后端。
- 设计清晰的数据层 / service 层，避免组件直接散落操作 localStorage。
- 首次进入显示“演示数据”提示。
- 提供“重置演示数据”按钮，恢复初始活动、用户、申请和消息。
- 可提供“切换演示身份”用于演示参与者和组织者流程，必须标注为演示工具。

## 7. 视觉要求

- 品牌：粉紫渐变主色、暖白 / 浅桃色背景、圆角卡片、清晰活动图片和标签。
- 保留年轻、友好、轻社交氛围，避免过度幼态化。
- 时间、地点、费用、名额和状态必须清晰。
- 主要操作突出；危险操作二次确认。
- 所有按钮必须有动作；未实现功能应隐藏或明确标记“后续规划”，不能制造假功能。
- 图片提供占位与失败回退；窄屏布局不能溢出。
- 支持键盘聚焦和表单错误提示。

## 8. 安全与隐私红线

- 不请求精确定位权限，不后台追踪，不保存真实坐标。
- 不拨打 110 / 120，不调用真实电话、短信、公安系统、支付或第三方服务。
- 紧急求助必须显示“演示功能：不会拨打电话或发送定位”，并经过确认步骤。
- 不采集身份证、真实手机号、通讯录或支付信息。
- 举报仅写入本地模拟数据，显示“已记录（演示）”。
- 不声称平台可保证线下绝对安全。
- 所有示例用户、头像、评价和运营数字均为虚构演示数据。

## 9. 分阶段开发

### Phase 0：仓库检查与计划

输出现状、技术栈、实施计划、潜在冲突。若仓库为空，再创建脚手架。

### Phase 1：设计系统与页面骨架

实现颜色 token、字体层级、按钮、卡片、标签、导航、toast、modal、empty state。 验收：页面导航可用，桌面和移动布局正常。

### Phase 2：活动数据与发现流程

实现 seed data、活动列表、搜索、筛选、详情、创建活动。 验收：创建活动出现在列表中，筛选真实改变结果。

### Phase 3：申请与组织者流程

实现申请加入、申请状态、组织者通过 / 拒绝、成员列表、我的活动状态。 验收：通过人数不超上限；重复申请被拦截；参与者能看到更新状态。

### Phase 4：活动闭环

实现群聊、模拟签到、开始 / 结束活动、评价、旅行名片。 验收：可从准备中走到已结束；刷新后关键状态仍存在。

### Phase 5：安全与内容辅助模块

实现安全中心、举报、退出活动、路线节点、同城内容流、个人资料编辑。 验收：演示边界清楚；无真实定位、电话或外部数据发送。

### Phase 6：QA 与交付

- 运行 lint / typecheck（若配置）和 production build。
- 修复控制台错误、路由错误、表单边界、状态同步和响应式问题。
- README 写出安装、启动、演示流程、测试结果、已知限制。
- 若有 Playwright，覆盖创建活动、申请加入、审核、评价主流程；若没有，不要声称自动化测试已执行。
- 最后列出已完成 / 未完成 / 已知问题 / 下一步建议。

每阶段完成后先自测，再进入下一阶段。不要在没有运行构建的情况下宣布项目完成。
