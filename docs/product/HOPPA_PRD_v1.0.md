## 1. 产品概述

### 1.1 产品定义

HOPPA 是一款面向年轻人的同城轻社交与活动组队产品。用户围绕 City Walk、城市漫游、展览、演唱会、桌游、运动、美食探索等具体活动，发现同好、发起活动、申请加入、共同规划路线，并在活动后留下评价和旅行名片。

### 1.2 核心定位

**不是再做一个泛社交聊天软件，而是让“想一起做一件事的人”更容易从线上匹配走到线下见面。**

- 核心承诺：用明确的活动信息降低组队成本，用偏好匹配提高活动适配度，用活动流程和安全提示提升线下参与的确定性。
- 产品口号：线上相遇，线下来聚。
- 首发场景：武汉同城，年轻人周末及晚间的短时活动。
- 核心差异：以“活动”为关系起点，而非以“陌生人私聊”为起点；强调活动信息透明、轻量申请、共同参与和活动后反馈。

### 1.3 第一版产品形态

第一版交付为响应式 Web 应用 / PWA 风格原型，优先支持桌面浏览器演示，并兼容手机屏幕。它不是正式上线的真实社交服务，也不应声称已接入真实定位、公安系统、实名认证或实时通讯。

### 1.4 产品设计原则

1.  **活动优先**：用户先看到做什么、何时、在哪里、多少钱、还缺几个人，再决定是否加入。
2.  **轻关系、强边界**：个人信息默认最小化；用户可以不填写 MBTI，不因拒绝私聊而影响活动参与。
3.  **规则透明**：展示活动人数、费用方式、出行方式、主办者和活动状态。
4.  **从线上到线下闭环**：发现—查看—申请—确认—参加—评价—分享，不能只做静态展示。
5.  **安全不夸大**：演示版安全中心只提供流程模拟和安全提示，不宣称能实时定位、联系警方或保证人身安全。
6.  **先验证核心价值**：不把 3D 元宇宙、复杂推荐算法、商城和商业合作作为首版依赖。

## 2. 用户问题与产品假设

### 2.1 需要解决的问题

| 用户问题                     | 典型表现                                           | HOPPA 的产品应对                                     |
|------------------------------|----------------------------------------------------|------------------------------------------------------|
| 想参加活动，却找不到合适的人 | 社交平台信息零散，活动时间、地点、费用和人数不统一 | 结构化活动卡片与筛选                                 |
| 想找搭子，但不想高投入社交   | 直接私聊陌生人压力大，关系目标不明确               | 以共同活动为起点，优先展示活动与共同兴趣             |
| 看到活动后难以判断是否适合   | 缺少费用方式、参与人数、出行偏好等信息             | 活动详情展示关键约束                                 |
| 发起活动后组织成本高         | 招募、确认、通知、集合和复盘分散                   | 活动管理、申请状态、群聊、签到与评价流程             |
| 线上匹配难以转化为真实见面   | 匹配后没有明确下一步                               | 将匹配结果导向活动详情、加入申请和活动管理           |
| 对陌生人线下活动存在顾虑     | 组织者不清楚、临时变更、个人信息暴露               | 展示组织者和规则，提供举报、退出、集合信息与安全提示 |

以上是基于原始方案提出的问题框架，仍需通过用户访谈或可用性测试验证，不将其视为已完成的用户研究结论。

### 2.2 目标用户

**核心用户：18 岁及以上、在武汉学习或工作、希望通过具体活动拓展同城体验的年轻人。**

| 用户类型   | 目标                     | 主要顾虑                           | 产品机会                         |
|------------|--------------------------|------------------------------------|----------------------------------|
| 活动参与者 | 快速找到周末可参加的活动 | 信息不全、匹配不合、陌生人社交压力 | 筛选、详情页、轻量申请           |
| 活动发起者 | 找到合适成员并完成组织   | 招募效率低、沟通分散、临时爽约     | 创建活动、管理申请、活动群聊     |
| 城市探索者 | 发现新地点并分享体验     | 攻略分散、路线难组合               | 城市内容、路线卡、活动后旅行名片 |

### 2.3 JTBD（用户待完成任务）

- 当我周末想出门但朋友时间不一致时，我希望找到时间、兴趣和预算合适的同城活动，以便不用独自做完所有计划。
- 当我想发起 City Walk 或桌游活动时，我希望一次写清时间、地点、人数和费用规则，以便减少反复解释。
- 当我考虑加入陌生活动时，我希望先了解活动内容、组织者和参与规则，以便在申请前判断是否适合自己。
- 当活动结束时，我希望记录体验并分享路线，以便保存回忆，也帮助其他人发现活动。

### 2.4 需要验证的产品假设

- H1：结构化活动详情能减少用户在申请前需要额外询问的信息量。
- H2：按活动类型、时间、预算、出行方式筛选，比仅靠泛化兴趣标签更能帮助用户找到合适活动。
- H3：将“申请加入—组织者确认—活动群聊—活动后评价”串成闭环，有助于提高活动完成率。
- H4：清楚展示费用、人数、集合点和安全规则，有助于提升用户参与信心。
- H5：活动后的路线名片和体验分享，可能成为下一轮活动发现与供给的来源。 这些是假设，不是已验证结论。

## 3. 产品目标与指标

### 3.1 MVP 目标

1.  用户可以发现并筛选同城活动。
2.  用户可以查看活动详情并提交加入申请。
3.  发起者可以创建活动、查看申请并管理活动状态。
4.  用户可以在“我的活动”中追踪准备中、进行中、待评价和已结束活动。
5.  用户可以完成一次模拟闭环：加入 / 发起 → 查看活动信息 → 群聊 → 模拟签到 → 完成活动 → 评价 / 分享。
6.  所有关键操作有明确反馈；刷新后，本地关键操作仍能保留。

### 3.2 核心指标建议

**北极星指标（试点阶段建议）：每周完成的有效活动数。**

“有效活动”建议定义为：状态为已结束、至少有 2 名参与者，且不存在被取消或标记为演示无效的情况。作品集原型只展示模拟数据，不得将模拟数据描述为真实运营结果。

| 指标           | 计算口径                                            | 用途                                       |
|----------------|-----------------------------------------------------|--------------------------------------------|
| 活动详情点击率 | 活动详情页浏览次数 / 活动卡片曝光次数               | 判断卡片是否吸引用户                       |
| 申请转化率     | 提交加入申请的去重用户数 / 活动详情页去重访问用户数 | 判断活动信息和加入意愿                     |
| 申请通过率     | 被组织者通过的申请数 / 有效申请数                   | 观察供需与筛选质量                         |
| 活动完成率     | 已完成活动数 / 已发布且到达活动时间的活动数         | 观察组织闭环                               |
| 评价完成率     | 提交评价的参与用户数 / 已完成活动的参与用户数       | 观察反馈闭环                               |
| 举报处理时效   | 从举报创建到状态更新的时间                          | 作为安全运营过程指标                       |
| 安全事件率     | 经人工核实的安全事件数 / 参与人次                   | 安全护栏；不能单纯以举报数量下降判定更安全 |

### 3.3 数据原则

- 原型中的统计数字、用户、评价和活动均为 mock 数据。
- 未接入真实数据分析服务前，只能验证事件是否正确触发，不能报告真实转化率。
- 指标口径应在开发前冻结，避免开发完成后更改分母或定义。

## 4. MVP 范围与优先级

### 4.1 P0：必须完成（核心闭环）

| 模块          | P0 范围                                                      | 完成标准                            |
|---------------|--------------------------------------------------------------|-------------------------------------|
| 首页 / 发现   | 活动卡片、分类入口、搜索、筛选、空状态                       | 可进入详情；筛选实际改变列表        |
| 活动详情      | 时间、地点、预算、费用方式、人数、标签、组织者、规则         | 信息完整；满员或关闭时不能申请      |
| 找搭子 / 匹配 | 个人活动与社群活动入口、偏好筛选、推荐列表                   | 可切换类型、筛选活动；推荐理由透明  |
| 创建活动      | 标题、类型、时间、集合地点、人数、费用方式、预算、描述、标签 | 校验通过后创建并出现在列表          |
| 加入申请      | 提交申请、重复申请拦截、申请状态                             | 有成功反馈；发起者可模拟通过 / 拒绝 |
| 我的活动      | 准备中、进行中、待评价、已结束、我发起的                     | 活动状态与操作按钮匹配              |

| 消息 / 群聊   | 活动群聊列表、消息展示、发送本地模拟消息                     | 消息即时显示并本地持久化            |
| 活动闭环      | 模拟签到、结束活动、提交评价                                 | 状态按规则流转                      |
| 个人中心      | 昵称、头像、兴趣标签、活动统计、旅行名片入口                 | 可编辑基础资料                      |
| 安全中心      | 安全提示、举报、退出活动、演示版紧急流程                     | 明确标记演示功能                    |

### 4.2 P1：有余力再做

- 城市内容流：活动照片、路线笔记、点赞 / 收藏 / 评论的本地模拟。
- 武汉路线推荐：黄鹤楼漫游、东湖 City Walk 等静态路线卡和路线节点列表。
- 活动后生成旅行名片，可复制分享文案或下载简版图片。
- 搜索历史、收藏活动、活动分享链接（本地模拟）。
- 简单活动推荐排序：兴趣标签、时间、预算、出行方式匹配；展示“为什么推荐”。

### 4.3 P2：不纳入本次作品集 MVP

- 真实 3D 城市元宇宙、可自由漫游的三维场景和 NPC。
- 真实身份 / 未成年人身份核验、证件信息采集。
- 实时 GPS 追踪、后台持续定位、真实一键报警或公安系统联动。
- 真实短信 / 推送、生产级即时通讯、在线支付和商城交易。
- 复杂机器学习匹配、真实地图导航、实时交通拥堵预测。
- 多城市运营后台、商家合作、会员付费与完整商业化链路。

**范围决策理由：**这些功能成本高、依赖外部服务或涉及敏感数据，且不是验证核心价值所必需。作品集应先证明核心用户流程成立，而不是用不可运行的按钮制造“功能丰富”的假象。

## 5. 信息架构

建议底部主导航（移动端）/ 左侧主导航（桌面端）： 1. 首页：活动发现、精选路线、热门分类。 2. 同城：城市内容与地点灵感。 3. 找搭子：个人活动 / 社群活动、筛选和匹配。 4. 发布：创建活动。 5. 我的：个人资料、我的活动、旅行名片、设置与安全中心。

全局入口：搜索、消息、安全中心；活动详情可从首页、同城内容、匹配结果、消息和个人活动列表进入。

## 6. 核心用户流程

### 6.1 参与者加入活动

首页 / 找搭子 → 选择类型与筛选 → 浏览活动卡片 → 查看详情 → 检查时间、地点、预算、人数与规则 → 提交申请 → 等待确认 → 进入活动群聊 → 查看集合点与路线 → 模拟签到 → 活动结束 → 提交评价 → 生成旅行名片 / 分享。

异常规则： - 活动已满：禁用申请按钮并提示“名额已满”。 - 活动已取消 / 已结束：不可申请。 - 用户重复申请：提示当前申请状态，不生成重复记录。 - 活动时间已过：不允许创建或申请过去时间的活动。 - 用户主动退出：二次确认并更新参与状态。

### 6.2 发起者创建并管理活动

点击发布 → 填写活动信息 → 表单校验 → 发布活动 → 进入准备中 → 查看申请人 → 通过 / 拒绝申请 → 查看成员与群聊 → 活动开始 → 模拟点名 / 签到 → 结束活动 → 提醒成员评价 → 查看活动回顾。

关键规则： - 发起者自动成为组织者，不需要再次申请加入。 - 已通过人数不能超过活动人数上限。 - 活动开始后，不能直接修改关键时间 / 集合地点；修改需明确提示成员。 - 活动结束后，详情保留，评价入口开放。

### 6.3 活动安全与隐私流程

活动详情 / 我的进行中活动 → 安全中心 → 查看活动信息和安全提示 → 选择“分享活动信息”“举报问题”或“退出活动”。“紧急求助”只模拟交互，不拨打电话、获取 GPS 或向第三方发送数据。

## 8. 业务规则与状态机

### 8.1 活动状态

- **准备中**：活动已发布，仍在招募或等待开始。
- **进行中**：活动已开始，签到和群聊入口可用。
- **待评价**：活动已结束，当前用户尚未提交评价。
- **已结束**：活动已结束且当前用户已完成评价，或无需评价。
- **已取消**：活动被组织者取消，不能继续申请；已报名成员可看到取消说明。

建议转移：准备中 → 进行中；准备中 → 已取消；进行中 → 待评价；待评价 → 已结束。不能由普通参与者任意修改全局状态；演示版可由组织者或明确的模拟推进操作触发。

### 8.2 申请状态

待审核 → 已通过 / 已拒绝 / 已撤回；已通过 → 已退出（若活动尚未结束）。已拒绝 / 已撤回不能自动变成已通过；重新申请需显式操作并防止重复记录。

### 8.3 费用规则

- 费用方式：AA 制 / 各自承担 / 免费 / 费用待协商。
- 预算字段为人均预估，不是支付承诺。
- 不实现支付和资金托管；不得将“平台确认”表述为真实支付保障。

### 8.4 匹配逻辑

首版不需要复杂 AI。排序优先考虑：活动可申请、时间尚未开始且仍有名额；用户选择的活动类型；预算范围；出行方式；兴趣标签重合度。展示透明推荐理由。MBTI 可作为可选标签，不作为安全判断、可信度判定或唯一匹配依据。

## 9. 数据模型（MVP）

| 实体           | 核心字段                                                                                                                                                                        | 说明                         |
|----------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------|
| User           | id, nickname, avatar, city, bio, interests\[\], tags\[\], transportPreference, budgetPreference                                                                                 | 演示用户资料，不保存证件信息 |
| Activity       | id, organizerId, title, category, city, startAt, endAt, meetingPoint, budgetMin, budgetMax, feeMode, maxParticipants, description, tags\[\], status, routePoints\[\], createdAt | 活动主表                     |

| ActivityMember | id, activityId, userId, role, attendanceStatus, joinedAt                                                                                                                        | 活动成员与签到状态           |
| Conversation   | id, activityId, memberIds\[\], updatedAt                                                                                                                                        | 与活动绑定的群聊             |
| Message        | id, conversationId, senderId, content, createdAt                                                                                                                                | 本地模拟消息                 |
| Review         | id, activityId, reviewerId, rating, tags\[\], comment, createdAt                                                                                                                | 活动后评价                   |

关系：一个用户可发起多个活动；一个活动可对应多个申请、成员、消息、评价和回顾；一个活动只有一个组织者，组织者自动成为成员；同一用户对同一活动的评价需唯一；MVP 使用 localStorage，后续接后端再迁移。

## 10. 视觉与交互要求

原型截图呈现出鲜明的 HOPPA 风格：粉色 / 紫色为主色、浅桃色或暖白背景、圆角卡片、轻松插画与头像、活动图文卡片、移动端底部导航。第一版保留品牌识别，同时优化信息层级和可读性。

- 主色：HOPPA 粉紫渐变；用于主按钮、重点标签和品牌识别。
- 背景：暖白 / 浅桃色，正文保持高对比度。
- 卡片：圆角 14–20 px，轻阴影或细边框，避免装饰挤占活动信息。
- 活动卡首屏必须展示标题、类型、日期时间、地点、预算 / 费用方式、已报名 / 总人数、发起者。
- 所有按钮必须有真实交互；不可只做装饰。
- 统一加载中、空状态、错误、成功和危险操作二次确认。
- 桌面端使用可浏览的完整布局；手机端使用底部主导航。

## 11. 技术实现边界

### 11.1 推荐技术路线

- 前端：React + TypeScript + Vite。
- 样式：Tailwind CSS 或项目现有样式体系。
- 图标：Lucide；路由：React Router。
- 数据：mock seed data + localStorage。
- 测试：覆盖关键状态流转与表单校验；有条件可用 Playwright 自动化。
- 首版不要求后端、数据库、账号服务或外部地图 API。 如已有代码仓库，先识别现有技术栈并沿用，不为套用推荐方案重写已有项目。

### 11.2 演示数据要求

- 提供 10–15 条可筛选的武汉活动示例，覆盖 City Walk、美食、展览、桌游、运动和演出。
- 至少 2 条活动可完整演示申请 / 管理 / 评价闭环。
- 时间、预算、人数和地点需自洽。
- 提供“重置演示数据”入口。
- 标记“演示数据”，避免被误认为真实用户或运营数据。

## 12. 隐私、安全与合规护栏

1.  首版定位为 18 岁及以上用户的作品集演示原型，不采集真实证件、精确 GPS、通讯录或支付信息。
2.  不申请定位权限，不后台追踪，不自动向其他人暴露用户位置。
3.  紧急求助只模拟交互；不得自动拨打 110 / 120，不得声称与警方联网。
4.  群聊和举报为本地模拟，不将内容发送到外部服务。
5.  举报理由可选：骚扰 / 虚假信息 / 费用争议 / 安全风险 / 其他；提交后显示“已记录（演示）”。
6.  提供退出活动、举报入口；明确哪些操作仅为演示。
7.  真实上线前需单独评估个人信息保护、未成年人保护、内容审核、线下活动责任、紧急事件响应与第三方服务接入。

## 13. 验收标准

### 13.1 功能验收

- 从首页完成浏览、筛选、详情、申请加入。
- 发起者创建活动、审核申请并查看成员。
- 我的活动分类与活动状态一致。
- 活动状态按规则流转，不能跳过状态。
- 群聊消息、资料修改、申请和评价刷新后仍可恢复。
- 满员、重复申请、取消、过去时间、必填项缺失等边界场景有处理。
- 安全中心明确标记演示边界，不触发真实电话、定位或第三方服务。
- 桌面和移动端均可使用；关键按钮无遮挡。
- `npm run build` 成功；README 含安装、启动、演示路径和已知限制。

### 13.2 可用性验收

邀请 3–5 位目标用户或同学完成以下任务并记录结果： 1. 找到一个预算在 100 元以内、周末可参加的活动。 2. 判断活动是否适合自己并提交申请。 3. 创建一个 City Walk 活动并设置人数上限和费用方式。 4. 找到进行中的活动并完成模拟签到。 5. 对已结束活动评价并查看旅行名片。

观察任务完成率、完成时长、误操作次数，以及用户是否能准确复述活动时间 / 集合地点 / 费用方式。样本量小时只作探索性结论，不做统计显著性宣称。

## 15. 待确认事项

- 求职目标更偏 C 端产品、AI 产品还是平台产品；这会影响作品集叙事重点。
- 是否将路线规划作为主卖点，还是作为活动匹配的辅助能力。
- 是否已有真实访谈、问卷或可用性测试；没有则标注为待验证假设。
- 原型中的历史市场数据需重新核验后才能对外陈述。
- 若未来接入地图、AI、登录、推送或后端，需另立技术与隐私评估。

## 16. 项目完成定义

当作品能在浏览器中稳定运行，核心流程完整，关键状态可持久化，异常场景有反馈，README 能指导他人启动，测试清单通过，且作品集能解释产品取舍和待验证假设时，才算完成第一版。

**最终标准不是“页面像 App”，而是“陌生人能否不靠口头解释，独立完成一次找活动、加入活动、参加活动、活动后评价的流程”。**
