# 作品集叙事与面试要点

> 原则：如实区分原始方案、本次产品重构、AI 辅助实现与尚未执行的验证。
> 不要把「计划」写成「成果」，也不要把「页面数量」当成产品能力。

## 1. 推荐标题与一句话介绍

**HOPPA｜从"搭子文化"到活动闭环的同城轻社交产品重构**

HOPPA 面向希望通过具体活动拓展同城体验的年轻人，围绕活动发现、偏好匹配、组队管理与活动后分享，
降低从线上认识到线下参与的组织成本。本次交付为可交互 Web MVP（15 个页面、完整主闭环、17 条端到端用例）。

1. **封面**：产品名、口号「线上相遇，线下来聚」、角色（产品定义 + AI 辅助实现 + 验收）、时间、在线演示链接/二维码。

8. **验证与结果**：真实执行了什么（47 单元测试 / 17 E2E / 构建通过 / 375px 检查），

9. **指标体系**：北极星「每周完成的有效活动数」；漏斗指标（详情点击率、申请转化率、通过率、活动完成率、评价完成率）；
   安全护栏（安全事件率、举报处理时效）。口径在 PRD 冻结。
10. **复盘与路线图**：做对的取舍、不确定的地方、下一步验证计划（见 `docs/decisions.md` §7）。

## 4. 面试高频问题

**为什么不先做 3D 元宇宙？**
成本高，且不是验证「用户能否找到合适活动并完成线下参与」的必要条件。先用活动卡、路线节点与轻量内容验证核心价值。

**为什么不用 MBTI 决定匹配？**
MBTI 是自我表达标签，不能代表真实行为偏好或安全性。首版用活动类型、时间、预算、出行方式做透明匹配，并展示推荐原因，
让用户能判断「为什么推荐给我」，也方便后续做可解释的排序迭代。

**如何解决冷启动？**
从一个城市、少量高频品类和明确时间段开始，用精选路线与示范活动提供初始供给；
先验证活动能被看见、申请、完成，再扩品类与城市。这是待验证策略，不是已验证结论。

**怎么定义成功？**
试点阶段用「每周完成的有效活动数」做北极星，配合详情点击率、申请转化率、活动完成率与评价完成率诊断漏斗；
安全指标作为护栏，不能只看转化。

**你如何用 AI 而不是依赖 AI？**
先定义产品范围、状态机、数据模型与验收标准，再分阶段生成代码；每阶段跑 typecheck / 单测 / 构建，
对安全边界、数据口径与最终结论负责。重点讲「我改了 AI 什么、拦住了什么」，而不是生成速度。

**这个项目的局限？**
本地存储、无后端、无真实地图/支付/通讯、未做真人可用性测试。局限写进了 README 与决策记录，不做包装。
