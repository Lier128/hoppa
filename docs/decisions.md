# HOPPA MVP — 产品与技术决策记录

> 这份文件回答两个问题：**为什么这样做**，以及**哪些东西故意没有做**。
> 面试时最值得讲的不是"页面数量"，而是取舍和边界。

## 1. 产品定位

**不做"陌生人私聊"，做"一起做一件事"。**

HOPPA 的关系起点是活动：用户先看到做什么、什么时候、在哪里、多少钱、还缺几个人，再决定是否加入。
因此首版的全部核心页面都围绕"活动信息透明度"展开（活动卡片 → 详情 → 申请 → 组织者审核 → 群聊 → 签到 → 评价 → 旅行名片）。

选择武汉作为首发城市，是因为原始方案与原型素材都来自武汉；演示数据使用真实地名（东湖绿道、黄鹤楼、昙华林、湖北省博、江滩等），
让"信息是否自洽"这件事可以被直接检验。

## 2. 范围取舍（P0 / P1 / P2）

| 层级 | 本版状态 | 说明 |
|---|---|---|
| P0 闭环 | ✅ 已实现 | 发现 / 筛选 / 详情 / 申请 / 审核 / 我的活动 / 群聊 / 签到 / 评价 / 安全中心 / 本地持久化 |
| P1 增强 | ✅ 部分实现 | 旅行名片、同城内容流（点赞/收藏）、透明推荐理由；活动分享链接与图片下载未做 |
| P2 暂缓 | ⛔ 明确不做 | 3D 城市元宇宙、真实定位与后台追踪、真实报警、实名/年龄核验、短信推送、支付、真实即时通讯、真实地图导航、复杂推荐算法 |

**为什么先不做 3D 元宇宙？** 成本高，且不是验证"用户能否找到合适活动并完成线下参与"的必要条件。
**为什么不用 MBTI 决定匹配？** MBTI 是自我表达标签，不能代表真实行为偏好或安全性；首版用活动类型、时间、预算、出行方式做透明匹配，并展示推荐原因。
**为什么没有真实地图？** 真实地图需要外部 Key、隐私评估与费用；静态路线示意 + 结构化节点已经能验证"路线信息是否够用"。

## 3. 关键技术决策

### 3.1 React + TypeScript + Vite，不用 Tailwind

- 页面数量多、组件复用高，TypeScript 能在编译期拦住"状态枚举写错""字段名不一致"这类问题。
- 样式选择 **CSS Modules + 设计令牌**，而不是 Tailwind：本项目大量使用品牌渐变、玻璃拟态、生成式封面，
  这些用 CSS 变量表达比堆 utility class 更可维护；同时保留 `tokens.css` 作为唯一颜色来源，避免页面里写死十六进制。
- 没有使用任何 UI 组件库：按钮、标签、弹窗、Toast、表单都按品牌重新做，保证视觉一致性。

### 3.2 数据层：reducer + 纯函数规则 + localStorage 适配层

```
页面 → useApp()（AppStore） → domain/rules.ts（纯函数，可单测） → store/reducer.ts（纯 reducer）
                                      ↓
                              persistence.ts（唯一 localStorage 出入口）
```

- 页面**不直接读写 localStorage**，也不散落状态判断；"能否申请/能否评价/能否开始活动"都在 `domain/rules.ts` 一处定义。
- reducer 是纯函数，全部状态流转都能用 Vitest 覆盖（本项目 45 个单元测试）。
- 数据结构带 `schemaVersion`，升级后旧数据自动重建，避免演示时读到过期结构。

### 3.3 路由用 HashRouter

作品集要部署到 GitHub Pages / 本地静态预览。HashRouter 让深链接（`#/activity/a_xxx`）刷新不 404，
不需要服务器 rewrite 规则，也不需要 404.html hack。代价是 URL 不够"干净"，对演示型产品可以接受。

### 3.4 生成式活动封面，而不是照片

原型截图里的活动图是真实照片（含第三方人物/演出海报），**没有可授权来源**。
所以封面用「品类渐变 + 品牌光斑 + 拼图纹样 + 品类图标 + 编号」生成：
既保留品牌识别（粉紫 / 拼图），又不会误用他人图片，还能保证 15 条演示数据的视觉统一。
首版没有引入任何外部图片请求，离线也能完整演示。

### 3.5 演示身份切换，而不是登录

面试官不应该为了看一个申请流程去注册账号。演示工具面板支持在 6 个虚构用户之间切换，
每个用户带着自己的活动、申请和会话，因此"参与者视角"和"组织者视角"可以在 10 秒内互换。
这是演示工具，不是产品功能，面板里明确标注了 DEMO。

### 3.6 埋点：本地模拟，只验证"触发是否正确"

`track()` 把事件写进 state（最多保留 300 条），可在演示工具面板看到计数。
这能验证"事件在正确时机触发、属性是否正确"，但**不能**推导任何真实转化率——
README 和作品集说明里都写清了这一点，没有把 mock 数据包装成运营结果。

## 4. 规则实现清单（与 PRD §8 对应）

| 规则 | 实现位置 |
|---|---|
| 发起者自动成为组织者，不用申请 | 创建活动时写入 organizer 成员 |
| 已通过人数 ≤ 人数上限 | `canApprove` + reducer 审核前校验 |
| 满员 / 已取消 / 已结束 / 已开始不可申请 | `canApply`（返回具体 code 与文案） |
| 同一用户不能重复申请 | `canApply` + reducer 二次防重 |
| 活动时间必须在未来 | `validateActivityDraft` + 表单逐字段错误 |
| 只有结束后可评价，且每人一次 | `canReview` + reducer 唯一性校验 |
| 状态流转不允许跳跃 | `canOrganizerAct`（准备中→进行中→待评价→已结束） |
| 组织者不能退出自己的活动 | `canLeaveActivity` |
| 签到仅进行中、仅成员、仅一次 | `canCheckin` + reducer 幂等 |
| 举报只写本地模拟数据 | `saveReport` → `reports[]`，状态 `recorded` |

## 5. 安全与隐私边界（写入产品而不是只写在文档里）

- 不请求定位权限、不读取 GPS、不后台追踪；安全中心明确写"不获取定位"。
- 紧急求助是确认框 + 文字说明，**不会**拨打 110/120，也不向任何第三方发送数据。
- 不采集手机号、身份证、通讯录、支付信息；演示用户全部虚构。
- 举报只写本地模拟数据，显示"已记录（演示）"。
- 文案不承诺"全程监管""绝对安全""实时保护"。
- 静态路线页明确标注"示意，不是实时导航"。

## 6. 明确未做 / 已知局限

1. 没有后端、账号体系和多端同步，刷新保留依赖浏览器 localStorage；换浏览器/清缓存会回到演示初始数据。
2. 组织者不能修改已发布活动的集合地点/时间（需要"通知成员"的完整设计，首版只做了禁用说明）。
3. 群聊是本地模拟，没有真实即时通讯、没有未读数、没有已读回执。
4. 分享只能复制文案，没有生成图片/分享链接。
5. 没有接入任何真实地图、短信、推送、支付。
6. 可用性测试尚未执行（计划见 `docs/user-testing-plan.md`，测试结果出来后应回填）。
7. 移动端按 375px 宽度验证；未在真机 iOS/Android 上做兼容性测试。

## 7. 下一步（按优先级）

1. 做 3–5 人的任务测试，记录任务完成率、卡点与"能否复述时间/地点/费用"（验证 H1/H4）。
2. 补"组织者修改集合点 → 通知成员"的完整流程（这是线下活动的真实高频场景）。
3. 把活动分享做成真正的可传播链接（需要后端或静态数据编码方案）。
4. 若验证了"活动后发现内容"有价值，再做 P1 内容社区（点赞/收藏/评论）。
5. 后端与账号：至少在接真实用户前完成最小账号体系与内容审核方案。
